# 客户端 Web UI 独立发布计划

状态：方向已确认，实施与验证进行中。实现说明见 `docs/web-ui-updates.md`。

## 目标与范围

Android 和 macOS 安装一次支持新机制的客户端后，界面与前端逻辑更新无需重新安装 APK／App。Web UI 仍需要构建和发布，但不再触发原生编译、签名、公证、系统安装。

第一期覆盖目前使用的 Android APK 和 macOS 直装版。iOS、Windows、Linux 保留扩展接口，进入实际发布前分别验证运行时与分发渠道要求，不承诺各平台一次全部切换。

## 已确认现状

以当前 RC 源码 b96b848 为实施基线；工作目录的旧分支不能直接当作最新客户端基线。

- 手机、桌面已经使用 Tauri WebView；共用 `packages/app` 的 React / Expo Web 导出资源。
- `packages/desktop/src-tauri/tauri.conf.json` 的 `frontendDist` 指向 `../../app/dist`，因此 UI 改动目前随原生包发布。
- `mobile_hub.rs` 有旧版直接加载用户指定 Hub 网页的路径；已加密配对的客户端留在本地 UI，通过 `secureTransport.ts` 调用 Rust 的加密请求与终端通道。
- `mobile_shell.rs` 的导航限制、Tauri capabilities、配对恢复都假定可信本地页面。更换页面来源需要一起处理，不能只换一个 URL。
- 原生壳还负责密钥保存、扫码、通知、剪贴板、链接打开、桌面托盘/快捷键、Hub 管理及整包更新。
- Hub 已支持 `--static-dir`，也可内嵌 UI；这是浏览器客户端资源入口，与已配对 App 的界面加载是两条路径。

## 方案选择

| 方案 | 优点 | 主要代价 | 结论 |
| --- | --- | --- | --- |
| WebView 直接打开官方线上页面 | 发布与访问路径最简单 | 在线页面获得原生权限；网络、缓存、来源变化与启动恢复需要重新设计 | 可行，暂不作为默认路径 |
| WebView 直接打开各自 Hub 页面 | 自托管方便，已有旧版实现 | UI 与 Hub 版本绑定；让 Hub 控制拥有终端权限的页面，改变现有信任边界 | 保留旧入口，不用作新统一架构 |
| 原生壳加载经过签名验证的可更新 Web 资源包 | 前端独立发布；本地启动；保留加密连接与离线回退 | 需要实现资源更新器、兼容检查及回滚 | 推荐 |

推荐架构：官方资源发布服务 → 原生下载/验签/缓存 → WebView 加载本地已验证版本 → 原生 bridge → 用户已配对 Hub。资源服务不参与终端数据传输。签名保证发布来源，发布者仍是被信任的代码提供方；不能把签名描述成内容绝对安全。

保留现有 React / Expo Web 与 Tauri，不同时更换 UI 框架或重写终端。无需引入 React Native OTA 系统。

## 更新行为

1. 首次或离线启动使用包内版本或最近成功版本，检查更新不阻塞启动。
2. 原生在后台获取通道清单、检查兼容性、下载完整资源包并验证发布签名和文件哈希。
3. 写入暂存目录；完整校验成功后才标记为待启用。HTML、JS、CSS 属于同一个不可变版本，运行期间不混用两个版本。
4. 默认下次冷启动生效。有新界面时可显示轻提示“新版已就绪，重新打开后生效”；用户主动立即应用前保存未提交草稿和当前工作区，再重载及重连。
5. 不在输入、粘贴、交接或权限确认过程中自动刷新。服务端终端进程继续运行，但界面重载会重建连接，必须验证恢复效果。
6. 新版本启动后通过渲染与 bridge 就绪检查；连续失败回退至最近成功版本，再失败进入包内恢复页。Hub 离线不能被误判成 UI 损坏。
7. 恢复入口由壳提供，即使前端白屏也能切回已知可用 UI；清除 UI 缓存不得清除配对和密钥。

## 三条独立发布线

| 改动 | 发布方式 |
| --- | --- |
| 布局、文案、兼容现有接口的前端交互 | 仅发布 Web UI |
| 新增 Hub API、数据库迁移、Node 协议能力 | 更新对应 Hub / Node，并按需发布 UI；不当然要求客户端重装 |
| 新原生命令、扫码/通知插件、密钥实现、平台权限、原生故障修复 | 发布新版 APK / App |

UI、Shell、Hub/Node 分别拥有版本标识。UI 清单声明所需 bridge 版本与能力；壳不兼容时继续运行现有版本。Hub 能力在连接后协商，不因连接了旧 Hub 而让整个客户端无法打开；新功能降级或给出明确更新提示。

例如只调整布局或文案时只发 UI；新增一个 Hub API 时仍需更新 Hub。

## 分阶段实施与完成标准

### 1. 两端最小验证

- 在隔离分支上增加最小资源加载原型，验证 Android 与 macOS 都能读取应用私有数据目录的已验证资源。
- 优先保持现有本地 origin；具体采用资源协议拦截还是受控本地协议，由原型验证决定。不得假设动态目录可以直接替换 `frontendDist`。
- 验证 Tauri IPC、CSP、导航限制、静态路由/资源路径、localStorage、配对恢复、中文输入及终端通信。
- 用同一个安装包先加载 UI A，再下载 UI B；两端均实际看到变化，保留配对，无需安装新包。
- 如果无法保持同一 origin，先设计存储迁移和能力授权，再评估是否继续此路径。

交付：可运行的两端技术验证及明确架构决定。先跨过这个技术门槛，再扩大重构。

### 2. 原生资源更新器与兼容协议

- 增加 `ui_updates` 模块：检查、下载、签名校验、限额安全解包、暂存、原子激活、启动确认、失败回滚。
- 拒绝路径穿越、符号链接逃逸、不完整包、错误签名、未知平台和不支持的协议版本。
- 壳内置独立 UI 发布公钥；私钥只用于受控发布流程。定义公钥轮换与有序过渡机制。
- 清单包含 UI 版本、递增发布序号、通道、资源摘要、平台兼容范围、bridge 要求。普通下载不能回放陈旧清单；运营回滚通过更高发布序号指向已验证旧资源。设备本地故障回退不依赖网络。
- 提供稳定的 bridge 能力查询；将现有前端原生调用逐步收敛到适配层，不要求一次重写所有业务。
- 本地状态迁移保持至少前一版兼容；不可逆迁移不能随意伴随可回滚 UI 发布。

交付：断网、下载中断、白屏、损坏资源和不兼容版本均能恢复，配对数据不丢失。

### 3. Web UI 发布流水线

- 新增独立 UI workflow：类型检查、相关测试、Web 构建、资源清单、签名、不可变资源上传、RC 通道发布。
- 完整资源上传成功后再切换通道指针；保留历史资源和可操作的回滚入口。
- 初期仅 stable / RC 两个通道，先 RC 验证再晋升 stable；渠道默认由安装包确定，不给普通用户增加配置。
- 发布与原生工作流解耦；仅 UI 改动不触发 Android 或 macOS 原生构建。
- 明确资源托管地址、访问范围与缓存策略；地址尚未决定，不在规划阶段创建服务。
- 浏览器版继续部署相同前端源码产物到 Web/Hub 静态入口，不要求每个 Hub 立即改用同一更新器。

交付：一次 UI 发布能被已有两端壳获取；一次通道回滚能停止推广问题版本。

### 4. 产品体验与迁移

- 关于页显示应用版本与界面版本，检查更新自动区分 UI 更新和原生升级。
- 新机制首次上线仍需发一次 APK / App，保留现有签名、应用 ID、Hub 地址、配对密钥和工作区。
- 在新壳尚未普及时继续维护原有整包发布路径；不强制所有历史版本支持动态 UI。
- 默认下载最新兼容 UI，用户正常使用不需要选择参数；有平台差异时按壳能力处理。

交付：现有 RC 原地升级，之后连续两次前端迭代均无需重装。

### 5. 验证与推广

- 常规浏览器回归使用 `pnpm e2e:test` / `pnpm e2e:ci`，Chromium 在 runner 容器内运行。
- 原生 Rust 测试覆盖校验、兼容、原子激活、重放保护和回滚状态机。
- Android 模拟器与真实 macOS App 验证资源协议、IPC、冷启动、后台恢复、输入法、断网、更新中杀进程、保留配对升级。容器浏览器不能替代这些原生检查。
- 验证旧 Shell / 新 UI、旧 Hub / 新 UI、新 Hub / 旧 UI 组合，以及切换不同版本 Hub。
- 以一个小的界面改动作为首次仅 UI 发布验收：安装包版本和二进制不变，手机与桌面均出现新版界面；终端任务仍在、草稿可恢复。
- RC 稳定后推广到 stable，再评估其他平台。

## 主要成本与实施顺序

工作量主要在两端资源加载、稳定 bridge、故障回滚和发布兼容，不在重新写 UI。第一阶段结束后按实测问题估算剩余工期；现在不承诺未经验证的完成日期。

建议顺序：两端原型 → 更新器/兼容协议 → CI → 首个迁移 RC → 连续两次 UI-only 发布验收 → stable。
